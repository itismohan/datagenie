# Requirements: 0003-proposal-only-governance-workflows

## Functional requirements

| ID | Requirement | Acceptance criteria | Negative scenario |
|---|---|---|---|
| DG-PROPOSAL-001 | The platform SHALL persist a tenant-scoped `GovernanceProposal` aggregate containing type, title, structured change diff, source evidence, impact summary, initiator subject, initiating model/agent and host identities, policy decision snapshot, audit/request correlation, proposal hash, resource version preconditions, status, approval state, expiry, and execution outcome. | A created proposal can be retrieved only by its tenant and contains each required field, with secrets and raw tokens absent. | A cross-tenant lookup returns no proposal payload. |
| DG-PROPOSAL-002 | The platform SHALL create proposals idempotently using an actor-scoped idempotency key and canonical request hash. | Repeating the same request returns the original proposal; the proposal count remains one. | Reusing the key with a different body returns a conflict and creates nothing. |
| DG-PROPOSAL-003 | The platform SHALL capture a deterministic policy decision and evidence at proposal creation and reject creation when policy denies or cannot be audited. | A proposal stores decision rules, obligations, evidence references, expiry, and request correlation. | A failed policy audit, tenant mismatch, or denied policy results in no proposal. |
| DG-PROPOSAL-004 | The approval inbox SHALL show title, human-readable proposal text, structured diff, evidence, impact, initiating model/host identity, policy result, version preconditions, expiry, and explicit approve/reject controls. | A steward can list pending proposals and view the complete review record by proposal ID through REST and the inbox page. | An analyst or read-only user cannot approve or reject a proposal. |
| DG-PROPOSAL-005 | Approval SHALL issue a single-use confirmation nonce bound to the proposal hash, approver, approval version, and expiry. | An approved proposal returns a nonce; the nonce cannot be used twice and is not returned in unrelated proposal reads. | A supplied hash or nonce mismatch prevents execution. |
| DG-PROPOSAL-006 | Execution SHALL re-check tenant, current approver role, credential validity, proposal status, approval version, expiry, proposal hash, cancellation state, policy decision, and resource version preconditions atomically before any mutation. | A valid approved proposal applies its declared typed mutation exactly once and records execution audit evidence. | A revoked role, expired credential, stale approval, resource update, policy denial, cancelled proposal, or expired proposal causes no mutation. |
| DG-PROPOSAL-007 | The first release SHALL support typed proposal actions for asset curation, certification-review request creation, and quality-check scheduling request creation. | Each supported type has a validated diff schema, an impact summary, and a deterministic execution handler. | Unknown types, unbounded payloads, arbitrary URLs, arbitrary SQL, raw secrets, and direct job execution are rejected. |
| DG-PROPOSAL-008 | MCP SHALL expose only `create_governance_proposal`, `request_certification_review`, and `schedule_quality_check` as proposal-oriented tools, all returning structured proposal evidence rather than applying direct mutations. | `tools/list` advertises exactly the three approved proposal tools when proposal mode is enabled; tool results contain proposal ID, hash, status, source identity, policy, evidence, expiry, and inbox URI. | No MCP tool can call direct curation, certification decision, quality update, connector write, secret, export, SQL, or HTTP operation. |
| DG-PROPOSAL-009 | Every proposal lifecycle transition SHALL emit minimized tenant-scoped audit evidence correlated to the source policy decision and initiating host/model identity. | Create, approve, reject, cancel, execute, and blocked-execution events are auditable without raw prompts, tokens, or secrets. | Audit persistence failure fails closed for creation, approval, execution, or rejection. |
| DG-PROPOSAL-010 | Proposal execution SHALL be safe under duplicate, concurrent, and stale requests. | Concurrent confirmation attempts yield one execution and deterministic replay/conflict results; no duplicate mutation occurs. | A cancelled job, duplicate call, or changed resource version cannot race into a write. |

## Exit gate

A data steward can review, reject, or approve agent-created changes with sufficient identity, evidence, policy, impact, and version context. No model or host can mutate a governed resource through MCP without an inbox-approved, nonce-confirmed, re-authorized, version-valid proposal execution.
