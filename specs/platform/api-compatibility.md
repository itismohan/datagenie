# Platform Specification: API and Contract Compatibility

**Status:** Backfilled baseline
**Owner:** Platform API
**Constitution articles:** I, IV, V, VII, VIII, IX

## Intent

DataGenie SHALL provide stable, tenant-aware and supportable interfaces. Versioned API contracts, standard errors, request correlation, authorization, pagination/filtering bounds, idempotency, rate limits, OpenAPI documentation and compatibility discipline are product guarantees rather than framework defaults.

## Core requirements

| ID | Requirement | Required evidence |
|---|---|---|
| DG-API-001 | Business API endpoints SHALL be versioned under `/api/v1` until a documented major-version transition occurs. | Route and OpenAPI contract. |
| DG-API-002 | The executable OpenAPI contract SHALL expose curated tags, bearer authentication, reusable errors, request correlation, response codes, and interactive Swagger/ReDoc endpoints. | `/api/openapi.json`, committed artifact, contract-drift CI. |
| DG-API-003 | Protected operations SHALL enforce tenant-aware authorization and return safe `401`/`403` responses without cross-tenant existence leakage. | Security/session tests and OpenAPI documentation. |
| DG-API-004 | Errors SHALL use a consistent envelope with stable code, safe message, request ID and optional details. | Exception handlers and contract examples. |
| DG-API-005 | List/search interfaces SHALL define filtering, pagination or result limits, ordering/ranking behavior, authorization filtering and freshness semantics. | Schemas, persistent index behavior and tests. |
| DG-API-006 | Supported mutations SHALL define idempotency, concurrency/version behavior, audit trail and retry safety. | Idempotency records and endpoint contract. |
| DG-API-007 | Rate limiting SHALL be observable and fail closed outside development if its protection store is unavailable. | Redis-backed enforcement, headers, errors, metrics and alerts. |
| DG-API-008 | The search service SHALL delegate to the catalog discovery contract rather than return divergent stubbed results or bypass authorization. | Delegation tests and deployment configuration. |

## Compatibility policy

Additive operations, optional fields and new enum values are allowed in v1 when clients can safely ignore unknown values. Field removal/renaming, semantic type changes, authorization changes, altered error envelopes and changed mutation semantics are breaking. Breaking changes require a new major route or a documented migration/deprecation window, consumer notification and telemetry.

## OpenAPI and generated client discipline

The versioned OpenAPI artifact is generated by `apps/catalog-api/scripts/export_openapi.py`. CI regenerates the artifact and fails on drift. Public behavior changes must update the generated specification, the integration guide, tests and the relevant SDD traceability manifest.

## Failure behavior

When a dependency required for a safe response is unavailable, the API returns a correlated, bounded error rather than silently returning stale/unauthorized data. Public documentation endpoints are routed through the TLS ingress; metrics remain excluded from the public schema.
